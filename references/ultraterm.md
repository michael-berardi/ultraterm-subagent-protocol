# UltraTerm integration

Optional host mapping for USAP 1.8.0. Installing the portable skill does not implement these controls or change routing, credentials, dependencies, or global defaults. The public skill and bundled host skill have independent release histories.

## Inspect the running host

Use `ultraterm_subagents` for parent dispatch and `ultraterm_hub` for parent inspection and coordination. The hub exposes `list`, `status`, finite `wait`, `cancel`, `send`, `inbox`, metadata-only `diagnose`, and explicit `resume`. Tools may be exposed lazily after dispatch. Check the actual session schema: a checkout or installed package can differ from a running session. Children must not invoke parent dispatch or launch other agents.

A run requests one worker per task. How many run at once is set by host capacity: the machine, the operator's configured ceilings, and a provider that is rate-limiting; the rest queue and start as slots free. The dispatch tool's schema states the current maximum tasks per run. Select an authorized run-level `model` or `profile`, never both. Do not infer model/account availability, billing permission, or provider defaults from this mapping.

## Explicit budgets

- `timeoutMs`: default 600,000 ms (10 minutes), minimum 1,000 ms, maximum 28,800,000 ms (8 hours). This is an absolute run deadline including queue time.
- `maxTurns`: default 64, minimum 1, maximum 2048 assistant turns per worker. A larger ceiling requires an explicit budget; it is not the default.
- Native Pi compaction follows host settings; native retry is capped at one. Neither removes the deadline or turn guard. A budget stop can leave partial work; it is not a completed leaf or guaranteed closing report.
- Hub `wait.timeoutMs`: 0–30,000 ms. A wait timeout ends observation only; workers continue under their own budgets. Reviewer launch waits have an additional 60-second bound, capped by the run deadline. A zero-turn queue timeout is not a review.

Prefer foreground dispatch. Use `background: true` only when the parent has useful work during execution, then one bounded wait. Background is not detached execution.

## Intra-run DAG handoffs and board citations

- **Bounded intra-run dependencies (`dependsOn`):** A task may declare `dependsOn` listing sibling task labels or IDs to express a bounded acyclic handoff (such as `author -> verifier`) inside one `ultraterm_subagents` run. Dispatch validates the graph up front and fails closed on cycles or unknown references. Dependent tasks stay queued until all listed predecessors finish, then receive auto-forwarded compact predecessor pointers (label, state, worktree path/branch ref when isolated, and board sequence reference or bounded summary) without waking the parent for an extra round-trip. Because `timeoutMs` is an absolute run deadline including queue and wait time, set the run's `timeoutMs` to cover the entire dependency chain. If a predecessor fails, aborts, or times out, dependent tasks settle cleanly as aborted rather than hanging. Unbounded peer ping-pong loops are disallowed; the parent still owns final judgment and integration.
- **Zero-copy `#seq` / `seqs` board citations:** The run relay maintains a bounded, append-only per-run message log cleaned up when the run is retired. Workers with a board-read tool read entries non-destructively via `ultraterm_relay` with `operation: "read"` (supporting `afterSeq`, `seqs`, and `limit`), while existing destructive inbox polling remains separate for backwards compatibility. Parents fetch specific cited messages via `ultraterm_hub` `inbox` with `seqs`. Cite `#seq` references only when the recipient harness exposes a board-read tool; when a recipient cannot read the board (for example, harnesses that relay only through assistant text), pass a file path or a short bounded summary instead.

## Permissions, worktree isolation, and evidence

Read-only leaves omit `ownedPaths`. Editing requires `mayEdit: true` with exact exclusive `ownedPaths`; do not use broad parent directories to hide ownership conflicts. Guarded file tools enforce path checks, but `allowBash` grants unsandboxed shell access that can bypass ownership. Read-only Claude reviewers receive no Bash even if requested; stage evidence under cwd instead. These are tool controls, not OS isolation.

- **Automatic isolated git worktrees (`workspace`):** Dispatch supports `workspace: "auto" | "worktree" | "shared"` (default `"auto"`). Under `"auto"`, the host automatically creates isolated per-task git worktrees outside the repository tree (under a private session-temp or cache directory, never nested inside the repo) when a single run declares two or more tasks with `mayEdit: true` (regardless of `dependsOn` ordering) and `cwd` is a git repository with a valid `HEAD`. Each isolated worktree starts from the run's base `HEAD` commit (so sequential writers linked by `dependsOn` still target disjoint `ownedPaths` for parent merge, unless a host explicitly checks out a predecessor's committed branch). Single-writer runs and read-only leaves stay `"shared"` with zero worktree overhead. Worktree isolation does not relax exact, disjoint `ownedPaths` across concurrent writers, so branch merges avoid same-file conflicts. Isolated writers run with `cwd` pointed at their worktree across supported harnesses and return branch/diff receipts (`worktreePath`, `branch`, `baseCommit`, dirty status, diff summary). A read-only dependent (such as a verifier) running in the shared workspace inspects an isolated predecessor's changes only when the host grants the forwarded `worktreePath` as a read-only root or stages the diff summary under the verifier's `cwd`; inspecting a `baseCommit..branch` ref requires shell access and does not apply to read-only reviewers without Bash. Only provably clean worktrees (no uncommitted edits or unmerged commits) are removed automatically; dirty or committed worktrees (including aborted runs with partial edits) are retained for parent inspection, explicit resume, merge or cherry-pick, and cleanup. Startup orphan cleanup also follows the clean-only rule, removing only provably clean worktrees not referenced by any active, checkpointed, or resumable run while surfacing unreferenced dirty or committed worktrees rather than silently deleting them. The host never auto-pushes worktree branches, but a worker granted `allowBash` can still invoke `git push`. Worktree isolation avoids git index, lockfile, and build collisions, but is still not an OS security sandbox.

`requireImages: true` requests an advertised image-capable route; it is not proof an image was read. Inspect actual tool results and route receipts. Peer relay, native session continuation, warm forking, image transport, and permission rules vary by harness; do not assume native Pi behavior on another harness. Peer messages never authorize scope or permission changes.

## Checkpoints, warm forking, failover, and explicit continuation

A parent with a persistent session file retains private disk checkpoints and available native worker history. Memory-only operation has no durable recovery. Persistence errors and unreadable checkpoints must be surfaced rather than treated as healthy recovery.

- **Automatic mid-run in-place failover (implicit runs only):** On implicit route-chain runs where the parent did not pin an explicit route override, the coordinator populates configured alternates from the operator's routing policy (honoring capability tiers, `requireImages`, and exclusion flags). If a worker hits a transient mid-run provider failure (quota exhaustion or upstream 5xx errors), the coordinator can switch in place within those configured alternates while reopening the same persisted worker session file with a compact continuation prompt, recording route-fallback hops in receipts and progress views. Failover hops are strictly bounded to the configured alternates, consume the same run `timeoutMs` and `maxTurns` budgets rather than resetting them, and must stay at or above the leaf's required capability tier. Policy or content-filter refusals are not transient failures and must be reported to the parent as failures rather than routed around. Explicit routes remain strictly fail-closed and never switch silently.
- **Warm context-preserving `forkFrom`:** A task may specify `forkFrom: { runId, taskId }` to branch from an existing persisted worker transcript within the same parent session. The host validates the source session strictly against the current parent session store (cross-session references are refused) and copies only the session transcript file to a fresh forked path—never scratch, build, or worktree directories. Forked leaves run with fresh ownership, permission, and budget guards; support depends on harness transcript persistence (for example, native Pi sessions).

Host exit interrupts workers: checkpoints do not provide daemon survival. Reopen the same parent session, inspect `status` and `diagnose`, then explicitly request hub `resume` with that session's archived `runId`. Run IDs from another parent session are not authority to resume it.

Resume creates a successor run for unfinished tasks only; completed tasks never repeat. It preserves reasoning, permissions, ownership, original time/turn limits, and—except when the parent or operator explicitly supplies a replacement route (which must still stay at or above the leaf's required capability tier and satisfy `requireImages` when set) to recover a checkpoint stalled on quota or upstream failure—the original route, with fresh execution counters rather than increased limits. The inspected host permits one bounded continuation per task, not an unlimited resume chain. Active runs, already-resumed attempts, incompatible policy versions, unhealthy checkpoints, or started tasks lacking required history refuse continuation.

A continued worker uses available persisted history. Inspect partial edits and external side effects first: resume is not rollback, a transaction, or exactly-once execution. A refused continuation requires a newly scoped task, not silent route changes or budget inflation.

## Diagnostics and completion

`diagnose` reports state, budgets, observed turns, tool successes/errors, progress age, checkpoint health, persistence mode, truncation, and deterministic stall signals (`stalledTasks`, `unansweredRequests`, `awaitingDependencies`) where available. Idle-stream watchdogs pause during active tool execution and surface stalled streams cleanly without waiting out the full run deadline. Progress views report route-fallback hops, worktree branches, and dependency states deterministically; hosts must not spawn separate LLM narrator or monitor agents for status or stall polling. Inspect failure reasons, checkpoint errors, and warnings; do not read `done` alone as acceptance.

Background completion is intended to be buffered while the parent is busy and delivered at the idle boundary, without waiting for the next user message. Passive delivery does not trigger a model turn. Delivery receipts are checkpointed after host acceptance; a notice is not parent integration or verification.

## Verification scope

Checked on 2026-10-24: the current parent schema and live foreground dispatch, `status`, `diagnose`, and bounded `wait` were exercised. A completed-run `resume` request refused with no unfinished tasks; no successor was launched. Diagnostics reported checkpointed persistence and successful tool use. Budget defaults/ranges, resume guards, and passive delivery were also inspected in the installed host source. Those inspections do not prove crash/restart recovery, actual timeout enforcement, every harness, or idle-delivery timing end to end. The 1.7.0 intra-run `dependsOn`, non-destructive board reads (`operation: "read"` / `seqs`), automatic `workspace` worktrees, warm `forkFrom`, implicit mid-run failover, explicit resume replacement routes, idle-stream watchdogs, and deterministic stall diagnostics are documented here as optional target host contracts and were not part of the 2026-10-24 inspection; verify them against the running host's live schema and runtime tests before relying on them. Offline tests in this repository are synthetic documentation-contract checks, not host runtime tests. Revalidate those behaviors on the target host before relying on them.

The portable release does not bump a host checkpoint or telemetry schema. Honor the host's own compatibility checks rather than equating public skill versions with runtime schema versions.
